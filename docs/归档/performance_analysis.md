# 天玑 9400/9500 平台 RAW 图像处理性能理论分析报告

本报告针对 **4096 x 3072 (12.6MP)** 分辨率的 RAW 数据，在 **天玑旗舰平台 (Cortex-X4/X925 + 16GB RAM)** 环境下，对不同算法及存储格式的理论处理耗时进行深度分析。

---

## 1. 硬件背景与算力基准
*   **CPU**: 天玑 9400/9500 采用全大核架构，单核睿频超过 3.6GHz。支持 ARMv9.2 指令集及 SVE2 矢量加速。
*   **并发环境**: 项目已开启 `OpenMP` 动态调度（`#pragma omp parallel for schedule(dynamic, 16)`），可满载 8 个核心。
*   **内存带宽**: LPDDR5X 带来的超高带宽可确保 12.6MP (约 50MB 每帧) 的 Buffer 读写几乎无阻塞。

---

## 2. 处理流程复杂度分析

### 2.1 算法复杂度分级 (O-Notation)
1.  **None / RgbCh (线性采样)**: $O(N)$
    *   仅进行像素点对点的映射与简单的 2x2 均值计算。
2.  **Fast (双线性插值)**: $O(N)$
    *   每个缺失通道由周围 2-4 个像素线性加权，逻辑极简。
3.  **AHD / RCD (方向检测插值)**: $O(N \cdot K)$，$K$ 为 5x5 或 7x7 邻域
    *   涉及水平/垂直梯度计算、同质区域判断，计算量适中。
4.  **AMaZE / LMMSE (多尺度/最小均方误差)**: $O(N \cdot K^2)$
    *   涉及精细的边缘方向评估、迭代滤波，是目前 CPU 处理的上限。

### 2.2 存储格式开销
*   **JPEG**: 涉及颜色空间转换 (RGB -> YUV) 和 DCT 变换。虽有硬件加速可能，但 libjpeg-turbo 在天玑全大核上表现极佳。
*   **PNG**: 涉及 DEFLATE 压缩算法。其计算密度极大，且主要受限于单核串行性能，耗时通常是 JPEG 的 5-10 倍。

## 3. 理论处理速度耗时表 (12.6MP RAW)

| 处理环节 | 算法/格式 | 复杂度 | 核心占用 | 理论耗时 (ms) |
| :--- | :--- | :--- | :--- | :--- |
| **JNI Buffer 获取** | Direct Access | $O(1)$ | 1核 | < 1ms |
| **基础 Demosaic** | **RgbCh / Bin4** | 极低 | 多核 | 8 ~ 15ms |
| **标准 Demosaic** | **Fast (Bilinear)** | 低 | 多核 | 15 ~ 25ms |
| **中级 Demosaic** | **RCD / AHD** | 中 | 多核 | 45 ~ 80ms |
| **专业 Demosaic** | **AMaZE / LMMSE** | 高 | 多核 | 140 ~ 220ms |
| **后期处理** | WB/CCM/LSC/水印 | $O(N)$ | 多核 | 10 ~ 20ms |
| **编码与保存** | **JPEG (95% Qual)** | 高 | 多核 | 40 ~ 70ms |
| **编码与保存** | **PNG (无损)** | 极高 | 单核为主 | 450 ~ 900ms |

---

## 4. 全链路总时长预测 (全功能开启)

### 场景 A：极速记录 (Fast + JPEG)
*   **流程**: RAW -> Fast Demosaic -> Watermark -> JPEG
*   **预估总耗时**: **70ms ~ 120ms**
*   **体验**: 几乎感觉不到延迟，支持高速连拍。

### 场景 B：专业质感 (AMaZE + JPEG)
*   **流程**: RAW -> AMaZE Demosaic -> Watermark -> JPEG
*   **预估总耗时**: **200ms ~ 310ms**
*   **体验**: 明显的“转圈”处理感，但画质纯净。

### 场景 C：极限无损 (AMaZE + PNG)
*   **流程**: RAW -> AMaZE Demosaic -> Watermark -> PNG
*   **预估总耗时**: **650ms ~ 1100ms**
*   **体验**: 典型的后台任务，建议在后台 Service 中执行。

---

## 5. 性能瓶颈总结
1.  **PNG 编码**: 是整个管线中最慢的一环，天玑的高主频虽有缓解，但算法本质决定了其难以被并行化到极致。
2.  **JNI 反复转换**: 若在 Java 与 Native 间频繁传递大尺寸 Bitmap，GC 压力和内存拷贝会产生额外 30ms 左右波动。
3.  **计算 vs IO**: 天玑 9400 的计算能力远超 UFS 3.1/4.0 的写入速度，大量保存时瓶颈会转移到存储 IO。
